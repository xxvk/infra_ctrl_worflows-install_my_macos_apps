# FileVault: enabling and recovery-key escrow

Documentation only. `security_profile` in `scripts/macos_preferences.py`
already observes FileVault status read-only (`fdesetup status`); this
records the enable + recovery-key procedure that observation deliberately
stops short of, since enabling disk encryption is a security-posture change
requiring explicit user action — consistent with this skill's Safety rules
("never modify system or security settings automatically").

## Current status (observed 2026-07-19)

`fdesetup status` reports **FileVault is Off** on this Mac. This is a
read-only finding, not something this skill changed.

## Before enabling: decide where the recovery key goes

Enabling FileVault always generates a personal recovery key — a one-time
48-character code that decrypts the disk if the login password is lost.
This key is generated by macOS at enable time; **no script here ever
generates, displays, stores, or transmits it.** Decide *before* running
`fdesetup enable` which of these applies:

1. **Escrow with the user's Apple Account (recommended for a personal Mac)**:
   macOS offers "Allow my Apple Account to reset this disk" during Setup
   Assistant or in System Settings. This lets Account Recovery restore
   access without the user manually storing the 48-character key anywhere.
2. **Store the personal recovery key manually**: if Apple Account escrow is
   declined, the 48-character key must be written down and stored
   somewhere durable and independent of this Mac — a password manager
   secure note (this user's declared secrets manager is the system/iCloud
   Keychain; the Keychain itself does not have a "secure note" feature the
   way third-party managers do, so consider the Notes app with a
   passcode-locked note, or a physically printed copy in a safe). It must
   never be written into this repository, `state/`, or any Markdown file.

## Enabling (GUI path, preferred)

1. **System Settings → Privacy & Security → FileVault → Turn On…**
2. Choose the Apple Account escrow option unless there's a specific reason
   not to (e.g. a managed/enterprise Mac with an institutional recovery key
   policy — out of scope for a personal Mac).
3. Confirm the recovery key screen only shows once; if choosing the manual
   storage path, capture it immediately during that one-time prompt.
4. Restart when prompted; encryption then proceeds in the background and
   can be checked with `fdesetup status`.

## Enabling (CLI path, for scripted verification only — still an explicit user action)

```sh
sudo fdesetup enable
```

Run this from a visible Terminal so the user enters the admin password
directly; never pass or store the password in this skill. `fdesetup
enable` alone (without `-keychain` or an institutional key file) generates
a personal recovery key and prints it once to the terminal — this output
must not be captured, logged, or written to any file by this skill.

## Verification

```sh
fdesetup status
```

Expect `FileVault is On.` (or `Encryption in progress`, which becomes `On`
once finished). Do not consider the bootstrap complete on a Mac meant to be
encrypted until this shows `On`.

## What this skill will and won't do

- Will: observe and report current status (`security_profile` in
  `scripts/macos_preferences.py`), and document this procedure.
- Will not: run `fdesetup enable` unprompted, choose the recovery-key
  option on the user's behalf, or ever handle/store the recovery key
  itself. Enabling FileVault remains an explicit, user-confirmed action
  every time, exactly like the Gatekeeper policy change documented
  elsewhere in [SKILL.md](../SKILL.md#developer-machine-gatekeeper-policy).
